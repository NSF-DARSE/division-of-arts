The problem, plainly0:30

The calendar is only as complete as people's memory

DelawareScene.com is the state's public arts calendar. It fills up one way: a grantee organization remembers to log in and submit an event. If a theater forgets, the show simply isn't on the state calendar — and a resident looking for something to do that weekend never learns it exists.

So Division staff spend their time chasing organizations for listings instead of supporting the arts. Meanwhile the events are all sitting in public, on the organizations' own websites, already published.

Our scope for three days: go get those events automatically, keep only the ones that belong on a Delaware arts calendar, drop the ones already listed, and hand back a file that fits DDOA's existing bulk-upload process. No new system for staff to learn.

What we found when we looked1:00

Most of these sites already publish machine-readable events

The obvious build is "point an AI at 100 websites." Before writing any of it, we probed all 104 sources. Most of them already hand out clean event data — you just have to ask correctly.

Half the sources need a model to read them — but they are the small half. The 45 structured sources carry 1,764 of the 2,272 events. That single measurement set the architecture.

Our approach1:50

Structure first. The model last, where structure runs out.

The model reads the tail

53 small-venue sites publish events as prose. Brandywine Baroque lists "Save the dates!" and twelve bare dates under two venue headings — the model returns twelve structured concerts. The alternative was 53 bespoke scrapers.

The model judges scope

An author talk at a library belongs on an arts calendar; story time and passport services do not. 901 events needed that call.

Code does everything else

Dates, prices, phone numbers, categories and geography are parsed and validated deterministically. The 78% costs nothing and returns the same answer every run.

The hard part3:00

Filters that are right about the exception, not just the average

Anyone can write a keyword filter that works most of the time. Everything below is a real case from the live data where the obvious rule is wrong — and each one is now a regression test.

Demo & adoption4:45

DDOA could run this next week

We built a working mock of DelawareScene's intake and put it on AWS, so the whole loop is demonstrable rather than described — and the output drops straight into the process they already have.

It fits the existing process

Output is DDOA's own 13-column bulk-upload workbook — the same file a grantee would email in. No new system, no migration, no retraining.

Duplicates are caught on the way in

The calendar is pre-loaded with the 660 events DelawareScene already lists. Upload the same file twice and the second one adds nothing.

A human stays in the loop

The pipeline proposes; it never publishes. 352 rows carry a flag — usually a venue needing a directory entry first — so review effort lands where it is needed. Nothing is dropped silently.

Built to run unattended

Every stage is idempotent and checkpointed, designed as a nightly job that emails staff a workbook and a review report. 78% of events cost nothing but bandwidth.

Running on AWS

The site is deployed to EC2 by a script that resolves the VPC and current AMI at run time and boots gunicorn under systemd — so the demo is a URL, not a laptop. The pipeline stays a batch job; only what people read is hosted.

What deploying taught us

Running somewhere clean exposed what a laptop had been hiding: the site silently depended on the pipeline's local database for venue names, and two web workers raced to seed the same SQLite file. Both are cheap to fix once and invisible until you leave your own machine.

The wider point for the state: nothing here is specific to arts events. Probe sources, prefer structure, use a model only where structure runs out, dedupe against what exists, hand a human a reviewable file — that shape fits any agency aggregating public information it does not own.

Responsible AI & what we're handing over5:45

We treated the model as a component that fails

"Couldn't look" ≠ "found nothing"

An early run hit a rate limit, silently fell back to keyword rules, and reported zero events for 53 sources — while overwriting their good data. Extraction now fails loudly, and a failed pull never deletes what it had.

The budget is never a silent arbiter

If the AI budget runs out before every event is judged, the report says how many that affected and what to re-run. Our final run: zero.

Adversarially reviewed

Two multi-agent passes over our own code produced 35 findings reproduced against live data — a wrong venue ID, ticketed events priced as free, a Pennsylvania garden in a Delaware calendar. All fixed, all now tests.

Confidence is not correctness

Our favourite bug: the venue matcher scored any token subset 100%, so a bare "Newark" matched "Newark Arts Alliance" perfectly and attached the wrong VenueID — silently.
